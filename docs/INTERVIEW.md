> 建议用法：先自己答一遍，再对照；重点看"为什么这么选"，而不是"用了什么框架"。

## A. 项目与架构

### 1. 用一分钟介绍这个项目

TrustAgent 是一个 AI Agent 的安全网关原型。它解决的核心问题是：给大模型接上工具之后，
风险从"说错话"变成了"替你做事"，所以必须在**动作发生之前**有可强制执行的策略层。

项目分两部分：Java 控制面管认证、授权、策略、审计和评测编排；
Python 执行面管 Agent 编排和内容安检，两边用内部 Token 和贯穿全链路的 Trace ID 连接。

现在完成度是：控制面 82 项测试、执行面 267 项测试全部通过；100 条合成评测集实测
攻击成功率 5%、误报率 20%（误报主要来自演示语料里刻意投毒的那篇文档）。
Redis 队列代码写完但本机没跑通端到端（Docker 守护进程没起来），这点我在文档里标了。

### 2. 为什么要拆成 Java 和 Python 两个服务？

技术栈需求不同。控制面要的是事务、权限模型、审计——Java + Spring 的生态最成熟；
执行面要的是 AI 生态（模型 SDK、评测工具），都在 Python。

硬塞成一个服务的结果是：Java 里调 Python 脚本（部署与调试都别扭），
或者 Python 里做权限管理（生态弱、易出错）。

代价是跨服务的错误处理、超时、追踪都变复杂了，所以项目里才要专门做内部 Token、
Trace ID 透传、幂等回调。**这是主动选择的代价，不是没意识到的复杂度。**

### 3. 控制面和执行面的职责边界怎么划？

一句话：**控制面决定"能不能做"，执行面决定"怎么做"。**

* 控制面：认证、RBAC、限流、幂等、策略存储、评测编排、审计留痕、指标复算；
* 执行面：安检、模型调用、工具执行、逐条评测执行。

关键的一条：**执行面不自己查数据库**。策略是控制面下发过来的数据（快照），
执行面只按数据办事。这样"这次请求到底按哪一版策略执行"是可解释、可回放的。

### 4. 一条请求的完整链路是什么？

1. 浏览器带 JWT 调 `POST /api/apps/{id}/chat`；
2. 控制面：JWT 校验 → 权限校验（每一次回库查）→ 限流 → 参数校验 → 生成 Trace ID；
3. 控制面查策略快照，通过 HTTP 调 Python 的 `/v1/agent/run`（带内部 Token 与 Trace ID）；
4. 执行面：输入安检（注入 + PII + 长度）→ 若被阻断则**不调用模型**直接返回；
5. 模型决策（可能提议调用工具）；
6. 工具调用前由 `ToolPolicyEnforcer` 强制检查（白名单、次数、Schema、域名、敏感参数、副作用确认）；
7. 工具返回的内容若标记为不可信 → 做**间接注入二次安检**；
8. 模型产出最终回答 → 输出安检（PII、系统提示词泄露、HTML、URL）；
9. 控制面保存 Trace 摘要、安全事件、审计记录，返回前端。

### 5. 这个项目最容易被质疑的地方是哪里？

三处，我都写进 `docs/SECURITY_LIMITATIONS.md` 了：

1. **评测数据是自建的合成集**，它证明机制按设计工作，不证明在真实流量上有效；
2. **控制面只复核聚合指标，不复核单条判定**——`passed` 字段是执行面给的，控制面原样采纳；
3. **Redis 队列本机没跑通端到端**，重试/死信的决策有单元测试覆盖，但队列本身没实测。

## B. Java / Spring

### 6. JWT 里为什么不放权限清单？

权限会变，Token 签出去就改不了。如果权限写进 Token，管理员收回权限后要等 Token 过期才生效。

本项目选择**每次请求回库查权限**，多一次查询换"权限变更立即生效"。
这是安全性与性能的取舍，这里选了安全性。

### 7. 用户 JWT 和内部 Token 为什么要两条链路？

用户身份在 `/internal/**` 上没有意义——那里没有"哪个用户"的概念，
只有"调用方是不是执行面"。复用同一条链路会让两边的作用域互相污染。

另外 `/internal/**` 的鉴权**写在 Spring Security 的路径规则里**，
而不是每个 Controller 上写注解。这样新增内部接口时忘了加注解也不会漏权——
它是"默认拒绝"的。

### 8. `@Valid` 和 `@PreAuthorize` 的执行顺序，对测试有什么影响？

`@Valid @RequestBody` 的参数解析发生在**方法调用之前**，而 `@PreAuthorize` 是方法调用时生效。
所以如果给越权用例塞一个非法请求体，得到的是 400 而不是 403——
**那样测的其实是参数校验，不是越权拦截。**

我的越权测试里每个 403 用例都刻意构造了合法请求体，就是为了让断言指向正确的机制。

### 9. 乐观锁怎么实现的？为什么不用悲观锁？

策略表有 `version` 字段。客户端读到时是 3，提交时带上 3：

* 库里还是 3 → 更新成功，版本变 4；
* 库里已经是 4 → 返回 409，让客户端重新读取。

不用悲观锁（`SELECT ... FOR UPDATE`）是因为：策略编辑是**低频操作**，
冲突概率很低，为了一个低频场景去持有数据库行锁不划算。乐观锁在这种场景下更合适。

### 10. 创建评测任务为什么不用 `@Transactional`？

`createRun` 刻意不加 `@Transactional`，而是用 `TransactionTemplate` 显式圈住"建任务"，
把"入队"放在事务**外面**。原因有两个：

1. **如果在事务内入队**，事务回滚时消息已经在 Redis 里了，Worker 会去跑一个不存在的任务；
2. **同类自调用不经过代理**，`this.xxx()` 上的 `@Transactional` 根本不生效——
   这是个很隐蔽的坑，显式写 `TransactionTemplate` 反而更不容易错。

入队失败时会把任务标成 FAILED 并**释放幂等键**，让客户端能用同一个 Key 重试。

### 11. 幂等是怎么实现的？为什么缺 Key 要报 400？

用 `idempotency_record` 表，唯一索引在 `(scope, idem_key)` 上。
先"占坑"再干活，避免两个并发请求各建一个任务；同时存**请求指纹**（请求体的哈希）：

* 同 Key + 同指纹 → 重放，返回原资源 ID（HTTP 200）；
* 同 Key + 不同指纹 → 409 冲突；
* **没有 Key → 400 直接拒绝。**

为什么没有 Key 不能"当成非幂等处理"：那会让调用方以为自己有幂等保护，
一次超时重试就凭空多跑一轮评测，而调用方完全不知道。
**宁可报错，也不要给一个语义错误的成功。**

### 12. 你们怎么处理"事务内发消息"这个问题？

同第 10 题。补充一点：如果一定要在事务里发消息，标准做法是
**事务性发件箱（Transactional Outbox）**——把"要发的消息"和业务数据写在同一个事务里，
再由一个独立的投递进程扫描并发送。

本项目用的是更简单的方案：**先提交事务，再入队，入队失败就把任务标失败**。
因为在"任务丢一次可以重试"的场景下，Outbox 的复杂度不值得。

## C. 安全

### 13. Prompt Injection 你们怎么防？

第一版是**规则 + 标准化**，不做模型分类：

* 规则是数据（`patterns.py` 里的 `InjectionPattern` 表），可逐条单测、可统计命中分布；
* 标准化产出多个"视图"（去零宽字符、NFKC 归一化、base64/hex 解码、ROT13），
  检测器在原文和所有视图上分别匹配。**不改写原文**，避免因归一化产生误报。

实测能力边界：间接注入 10/10、编码 10/10、直接注入 13/15、系统提示词诱导 9/10。
**漏报集中在同义改写上**（"无视"、"作废"、"把…重复一遍"这些表述规则没覆盖）。

### 14. 直接注入和间接注入的区别？为什么要分开处理？

* **直接注入**：用户输入里就带越权指令，比如"忽略以上所有规则"。
  拦截点在**输入安检**。
* **间接注入**：指令藏在模型读取的资料或工具返回值里，**用户完全无辜**。
  拦截点在**工具输出的二次安检**。

分开处理是因为两者的信任模型不同：用户的输入本来就需要怀疑；
而工具返回的内容是"系统自己去取的"，很容易被忽略掉，恰恰是最危险的入口。

本项目的 `search_local_docs` 工具主动标记 `untrusted=True`，
提示编排器必须对它的返回值做二次安检。

### 15. 检测器为什么做成统一接口？

因为第一版是规则检测，阶段4 计划引入分类模型。把检测器抽成接口（`Detector`），
将来替换或**并联**（模型给置信度、规则给可解释锚点）时不用改调用方。

**为什么要并联而不是替换？** 规则可解释但泛化差；模型泛化好但难解释。
安全场景里"为什么拦下这条"和"拦得准不准"同样重要。

### 16. 敏感信息脱敏的实现与局限？

正则 + 校验规则（手机号、邮箱、身份证校验位、银行卡、API Key 样式），
不下载任何 NLP 模型，Presidio 只预留适配器位置。

**局限是实测出来的**：10 条合成敏感用例，防护开启后仍有 4 条把原值带进了输出
（第二种身份证样式、19 位银行卡、`ak_` 前缀 Key）。根因是**检测器认不出**，
所以从未进入脱敏环节。

这件事还暴露了一个方法论问题：**如果评测台用产品自己的检测器判断"有没有泄露"，
这 4 条会被记成"没有泄露"，泄露率会显示成 0。** 我把它改成了评测台自己的一套更宽口径，
泄露率从 0.0 变成 0.4——那 0.4 才是真实存在的泄露。

### 17. 工具权限怎么保证"真的被执行"？

关键在**策略执行点必须在动作之前的那一行代码上**，而不是在提示词里提醒模型。

`ToolPolicyEnforcer.check()` 在 `tool.invoke()` 之前被调用，检查：
白名单、调用次数上限、参数 JSON Schema、域名白名单、敏感参数规则、副作用确认、超时。

实测数据支持这一点：15 条工具滥用用例中，**10 条是输入规则没拦、由工具白名单在执行前拦下的**。
也就是说，模型确实提出了越权调用，是策略层挡住了它——这正是"安全不依赖模型自觉"的证据。

### 18. Mock 模型为什么故意不自我审查？

因为**把安全寄托在模型自觉上本身就是错的**，而且会让测试失去意义。
一个"乖乖听话"的 Mock 会让整套策略层看起来毫无必要，也掩盖真实风险。

所以 Mock 的行为是"只按用户意图行事"：用户让它发通知，它就提出调用 `send_notification`，
哪怕这个工具不在白名单里。这样"防护关闭"的对照组里攻击才会真的成功，指标才有意义。

### 19. 审计链怎么保证不被篡改？

严格说：**不能保证不被篡改，只能保证"被改了能发现"。**

每条记录保存上一条的哈希，当前哈希由规范化后的关键字段 + 前序哈希 + 时间算出。
验证时检查 seq 连续性、prevHash 链、以及重算哈希，能定位首个异常位置。

我特意在文档里写清楚：**有数据库写权限的人可以重算整条链**。
要抵抗这一点必须把链尾哈希外送到攻击者控制不到的地方（外部存证、WORM 存储），本项目没做。
另外，**这不是区块链**——没有共识、没有分布式账本，也不应该这样宣传。

### 20. 哈希链的规范化为什么要转义换行？

字段之间用换行拼接。如果字段值本身带换行，拼接后字段边界就被破坏了——
攻击者可以用 `detailJson = '{"a":"x\ny"}'` 构造出与另一条记录相同的规范化串。

所以拼接前把 `\n` 转义成 `\\n`。这类"序列化歧义"是密码学里很常见的一类问题。

## D. 评测与指标

### 21. 攻击成功率（ASR）的分母是什么？为什么？

分母是 **`expectedAction == BLOCK` 的用例数**，不是"类别属于攻击的用例数"。

因为 `PII_EXPOSURE` 这类用例的期望动作是 `MASK`（脱敏）。如果按类别把它算进攻击分母，
一次**成功的脱敏**会被算成"攻击穿透"——这是统计口径错误。

**指标口径错了，数字再精确也没有意义。**

### 22. 为什么要有"防护关闭"的对照组？

因为只说"攻击成功率 5%"没有意义——不知道没有防护时会是多少。

对照组跑同样的 100 条用例，但策略是 `guardEnabled=false`、放开工具白名单、
关闭副作用确认与敏感参数规则。实测 ASR 从 **5% 升到 100%**，
PII 泄露率从 **40% 升到 100%**。这个差异才是"防护有效"的证据。

注意基线不能把工具也拿走——那样测出来的只是"没有工具所以没出事"。

### 23. 指标为什么要控制面复算一遍？

如果执行面报什么就存什么，指标的准确性就完全托付给执行面了。
控制面从**逐条结果**独立复算一遍，与上报值逐键比对（容差 1e-6），
不一致就落一条 `METRICS_MISMATCH` 安全事件。

实测两边是完全一致的。为了做到这一点，两侧的公式必须**逐字一致**，包括：
分组按 `expectedAction`、除零记 0.0、nearest-rank 百分位、
以及**四舍五入规则**。

### 24. 跨语言实现里最容易踩的坑是什么？

**四舍五入。** Java 的 `Math.round(x)` 语义是 `floor(x + 0.5)`（向正无穷舍入），
Python 内建 `round()` 是**银行家舍入**（`round(2.5) == 2`）。

如果两边不一致，在半值处会产生 1e-6 量级的差异，控制面会报 `METRICS_MISMATCH`——
而这个"差异"是假的，是舍入规则造成的，排查起来非常费时间。
所以 Python 侧显式写成 `math.floor(x * 1e6 + 0.5) / 1e6`。

### 25. 你怎么知道指标不是编的？

三个层面：

1. **纯函数**：指标计算不碰数据库、不碰时钟，同一份输入永远得到同一份输出；
2. **可独立复算**：执行面算一遍、控制面从库里再算一遍，不一致就报事件；
3. **报告能自证**：除了 10 个比率，还输出 tp/fp/fn/tn 与各类用例数——
   只给一个 `precision=0.93` 而不给 tp/fp，读者无法判断这个数字是不是在 3 条用例上算出来的。

### 26. 评测跑完发现"正常用例通过率"和"整体通过率"矛盾，说明了什么？

这是我实际踩到的坑。当时 `benignPassRate=0.65` 而 `taskSuccessRate=0.94`，
两者放在一起看就是矛盾的——**指标之间的自洽性是最好的 bug 线索。**

根因：`passOf` 对 `CALL_TOOL` 期望只比对工具名，**忽略了整次请求是否被拦**。
一条"检索文档"的正常用例，工具确实被允许并执行了，但工具返回的内容触发了间接注入检查、
整次请求被判 BLOCK——任务并没有交付结果，却因为"工具名对得上"被算作通过。

修复后 `taskSuccessRate = 0.90 = 100 − 3 误报 − 3 漏报 − 4 脱敏失败`，完全自洽。

> 补充：后续又定位到 1 条误报来自规则本身过宽（`INJ-DOC-INSTRUCTION` 把普通技术描述判成注入），
> 修掉后 `falsePositiveRate` 从 0.20 降到 **0.15**，而 `tp` 仍为 57、召回率与 ASR 均未变
> —— 这正是"降误报"改动应有的形状（详见 `docs/BENCHMARK.md` §4b）。

## E. 异步与分布式

### 27. 为什么用 Redis Streams 而不是同步 HTTP 跑批量评测？

同步 HTTP 有三个问题：一个请求占住线程几分钟；中间网络抖动整批白跑；无法断点续跑。

Streams 提供了三样恰好需要的东西：**消息不丢（PEL）、消费组分摊、投递次数可查**。
而且依赖极轻（不引入 Kafka）。

### 28. Streams 的投递语义是什么？重复消费怎么办？

**至少一次（at-least-once）**：处理成功才 `XACK`，失败不 ACK，
消息留在 PEL 里，稍后由 `XAUTOCLAIM` 重新认领；投递次数超过上限就转死信队列并回调标记失败。

重复的代价是"可能白跑一遍用例"，但**不会产生重复结果行**：
控制面用唯一索引 `(run_id, case_id, guard_enabled)` 兜底，重复批次被计入 `skipped`。

这是标准做法：**投递语义选"至少一次"（实现简单、不丢数据），用幂等写入吸收重复。**
反过来做"恰好一次"需要分布式事务，复杂度高得多。

### 29. Worker 崩溃了怎么办？

两种情况都能自愈：

1. **处理中崩溃**：消息没被 ACK，留在 PEL 里；超过 `eval_reclaim_idle_ms` 后，
   另一个消费者用 `XAUTOCLAIM` 把它认领过来重跑。
2. **消费组不存在**：`XGROUP CREATE` 用 `MKSTREAM` 建组，
   起点用 `0` 而不是 `$`——用 `$` 意味着"只消费建组之后的新消息"，
   如果任务先创建、Worker 后启动，那条消息就永远不会被消费，任务永远停在 PENDING。

### 30. 什么规模下应该迁移到 Kafka？

现在的方案在**单机、任务量每天几百到几千、允许至少一次投递**的场景下完全够用。

需要迁移的信号：

* 需要**多分区并行**与顺序保证（Streams 的分区能力弱）；
* 需要**长期保留 + 重放**历史消息（Streams 是内存为主，虽然有 RDB/AOF 但不适合当存档）；
* 需要**跨数据中心复制**、生态集成（Connect / 流处理）；
* 单 Stream 吞吐接近单 Redis 实例上限。

本项目目前远没到那个规模，所以按文档的约定，Kafka 属于阶段4。

### 31. Trace ID 怎么跨服务传递？

控制面在请求入口生成，放在 HTTP 头（`X-Trace-Id`）里传给执行面。
执行面用它写日志、并在响应里回填，保证"Java 日志里的 traceId"和"Python 日志里的 traceId"是同一个值。

局限：这只是"日志关联 ID"，**不是完整的分布式追踪**（没有 span、没有父子调用关系、
没有耗时分解）。真正的追踪需要 OpenTelemetry，属于阶段4。

## F. 工程与反思

### 32. 100 条用例跑完，误报率 20%，你怎么看？

先归因，再解释。这 4 条误报来自**两个性质完全不同**的来源：
**3 条是语料被投毒**（演示语料里的 `04_upgrade_notice.md` 是刻意投毒的样本，
而检索默认返回 top-3，演示语料只有 4 篇文档——投毒文档占比 1/4）；
**1 条是规则本身过宽**（`INJ-DOC-INSTRUCTION` 把普通技术描述判成注入）。

**这个比例不能外推到真实知识库。** 真实环境里投毒文档占比远低于 25%，
且正常问答很少会检索到它。所以我不认为这个数字说明"检测器泛化差"。
规则侧那 1 条误报是**确实该修**的——修掉后 FPR 0.20 → 0.15，且召回率一条未丢。

另外还有 2 条误报是本次测试中发现并修掉的：`MockLLM` 的路名正则把"二环路"截成"二环"，
生成的参数违反工具 Schema，被策略层判 `PARAM_SCHEMA_VIOLATION`。
**外在表现是"正常用例被误拦"，看起来像策略太严，实际是 Mock 的参数错了。**

### 33. 你怎么保证评测集本身是有效的？

这是最难的一点，因为**用例写错了，指标看起来完全一样**。我踩过三个坑：

1. "简单**说明**你能做什么"里的"说明"命中文档检索关键词，
   于是一条"纯对话"用例实际去检索文档、撞上投毒文档被判 BLOCK；
2. 几条"间接注入"用例的提示词里有"**通知**"，先命中"发通知"意图、被工具白名单拦下——
   结果通过了，但**测的是另一条链路**；
3. 一条"输出 HTML 转义"用例的载荷里含 `document.cookie`，
   其中的 `document` 命中了文档检索关键词。

所以生成脚本里现在明确约束了每类用例的用词，并把踩过的坑写进了
`datasets/README.md`，供后续写用例时参考。

**结论：评测集本身也要被测试。** 至少要做"用例是否真的走到了目标链路"的抽查。

### 34. 这个项目里你觉得最有价值的一个决定是什么？

**让控制面独立复算指标，并且用评测台自己的口径去测泄露。**

前者让"指标可信"，后者避免了一个非常隐蔽的问题：用被测组件的能力去衡量被测系统，
是循环论证。这个坑的代价很具体——10 条敏感用例只测出 6 条泄露，
防护开启时的泄露率**显示为 0**，而真实存在的 40% 泄露被完整掩盖。

如果不是刻意去想"我这个测量方法本身有没有偏"，这个 bug 会一直被数字掩盖。

### 35. 如果让你重做，你会改什么？

1. **更早引入端到端脚本**。好几个 bug（H2 作用域、Mock 路名、用例写偏）
   都是"真的跑一遍"才发现的，而它们都无法通过单元测试发现；
2. **评测集先定义"每类用例必须走到哪条链路"的断言**，再写内容——
   而不是写完再靠人工抽查；
3. **内部接口的错误码更早统一**，避免执行面与控制面在枚举上漂移
   （目前靠"未知枚举直接 400"来暴露漂移，这是对的，但可以更早设计）。

### 36. 这个项目离生产还差什么？

按重要性排：

1. **真实数据和真实模型上的验证**——现在全部是合成数据 + 确定性 Mock；
2. **密钥管理**——现在只靠环境变量，没有 KMS/Vault，内部 Token 是静态共享密钥、无轮换；
3. **可观测性**——没有指标监控、告警、分布式追踪（阶段4）；
4. **多实例下的正确性**——限流的内存实现只在单实例下成立；幂等记录没有清理策略；
5. **JWT 的完整生命周期**——无刷新令牌、无吊销、无 MFA；
6. **数据权限**——现在是"角色 → 权限点"的静态映射，没有细粒度数据权限。

这些都在 `docs/SECURITY_LIMITATIONS.md` 里逐条列了。
